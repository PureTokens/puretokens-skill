acceptance result. It applies to the recorded CLI version and architecture only;
it does not accept the Codex desktop UI, another OS, or Intel/Rosetta execution.

## Installation observations

1. The six Pure Tokens Skill directories and `.puretokens-executor` were absent
   from the actual default `$HOME/.agents/skills` directory before this run.
   Other existing Skills were not moved or removed.
2. Extracted the verified platform ZIP and ran its unmodified native Shell
   sync with `--host codex` and that extracted source. Installation exited 0
   in 814 ms, including the automatically attempted init.
3. All six Skills and exactly one platform executor were present at version
   0.18.1. The seven installed ownership inventories passed verification.
   The installed executable matched the candidate SHA-256.
4. The 53 unrelated sibling entries had unchanged names, inode identities,
   modes, sizes and modification times. This was a metadata comparison, not a
   read of their private contents.
5. A newly started real Codex process returned all six expected Skill paths
   from `skills/list` with `forceReload: true`, enabled, user scope and no
   corresponding Skill errors.
6. A new ephemeral, read-only Codex CLI conversation invoked the installed
   help-only Skill, successfully read its usage guide, emitted the requested
   completion marker and emitted `turn.completed`. The observed Skill command
   was a file read; no executor, installer, network-tool or configuration-read
   command was observed. Normal client model inference is not a Skill API call.
7. An explicit project target containing spaces and non-ASCII characters was
   installed from the preceding 0.18.0 source at commit
   `a1b72527e0f63de68e098a2bd9b0566ae7cd5fe2`, then upgraded using the extracted
   0.18.1 candidate. The upgrade took 559 ms and retained an unrelated sentinel
   file. A fresh Codex process discovered the six project-scope Skills at the
   expected version before and after upgrade; the global copies remained
   separate entries, not additional project installations.
8. The upgraded executor checksum and managed inventories passed verification.
   The candidate selector's read-only `verify-installed` command, bound to
   the candidate release manifest, left managed file bytes, modes and
   modification times unchanged. The project-target sync deliberately omitted
   the host so init was deferred; it did not retry the earlier connection check.

The discovery probe initially assumed one entry per Skill name and compared
`/tmp` paths literally. Codex returned both user and project entries and
canonical `/private/tmp` paths. The probe was corrected to compare real paths,
read the version at each returned path, and retain the other-scope count.
The corrected observations above passed without changing the product installer.

## Connection and remaining cases

Automatic init was observed after the successful default-directory install.
It stopped locally with `active_connection_not_puretokens`, before issuing a
fixed API request. No configuration value or credential was displayed, copied
or changed to make this pass. No retry or cross-host credential probe followed.
This is not evidence of a server failure or a rejected API credential.

Authenticated API, the five media-generation/edit cases, same-task resume and
native image/video attachment handoff were not executed and remain pending.
No paid media task was created. The installation remains in place; failed init
did not trigger rollback or reinstallation.

The help-only conversation completed, but its CLI process did not exit before
the 60-second harness deadline and required process-group termination. Its
final exit code was 0 and no model error event was recorded. Treat the completed
guide invocation separately from this unverified CLI shutdown behavior; do not
claim end-to-end command latency or clean CLI shutdown from this run.
